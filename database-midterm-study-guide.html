Database vs DBMS

Database
กลุ่มข้อมูลขนาดใหญ่ที่บูรณาการและสัมพันธ์กัน ใช้แทนส่วนหนึ่งของโลกจริง เช่น นักศึกษา รายวิชา และการลงทะเบียน
DBMS
ชุดซอฟต์แวร์สำหรับนิยาม เก็บ ค้นคืน แก้ไข ควบคุมความถูกต้อง ความปลอดภัย และการเข้าถึงพร้อมกันของฐานข้อมูล
Metadata
“ข้อมูลเกี่ยวกับข้อมูล” เช่น schema, ชนิดข้อมูล, constraints และสิทธิ์ ซึ่งเก็บใน data dictionary

ปัญหาของ File System

  • Redundancy & inconsistency: ข้อมูลซ้ำหลายไฟล์ แก้ไม่ครบจึงขัดแย้งกัน
  • Difficulty / isolation: คำถามใหม่ต้องเขียนโปรแกรมใหม่ ข้อมูลแยกหลายรูปแบบ
  • Integrity: กฎธุรกิจฝังในโค้ด กระจายและแก้ยาก
  • Atomicity: ระบบพังกลางงานอาจทำสำเร็จเพียงครึ่งเดียว
  • Concurrency: ผู้ใช้หลายคนแก้พร้อมกันทำให้ข้อมูลสูญหายหรือไม่สอดคล้อง
  • Security: ควบคุมให้เห็นเฉพาะบางข้อมูลได้ยาก

เหตุผลที่ใช้ DBMS

คุณสมบัติความหมายตัวอย่างคำอธิบายในข้อสอบ
Data independenceแยกรายละเอียดการเก็บออกจากโปรแกรมเปลี่ยนวิธีจัดเก็บหรือ index โดย application ไม่ต้องเปลี่ยน
Efficient accessใช้ storage, index และ query optimizationเลือกแผน query ที่ต้นทุนต่ำกว่าแทนการอ่านทุกแถว
IntegrityDBMS บังคับกฎกลางปฏิเสธ Enrollment ที่อ้าง student_id ซึ่งไม่มีจริง
Concurrencyควบคุม transaction ที่ทำพร้อมกันป้องกันยอดเงินผิดเมื่อมีการถอนพร้อมกัน
Recoveryคืนฐานข้อมูลสู่สถานะสอดคล้องหลัง failureการโอนเงินต้องสำเร็จทั้งหมดหรือไม่เกิดเลย
Securityกำหนดสิทธิ์ตามผู้ใช้/บทบาทเจ้าหน้าที่บางกลุ่มเห็นข้อมูลแต่แก้ไขไม่ได้

ระดับของข้อมูลและคำที่ชอบสับสน

Physical level
ข้อมูลถูกเก็บอย่างไร เช่น file organization, index, disk blocks
Logical level
เก็บข้อมูลอะไร มี attribute และ relationship ใด
View level
ผู้ใช้หรือ application แต่ละกลุ่มมองเห็นข้อมูลส่วนใด
Schema
โครงสร้างหรือแบบแปลน เปลี่ยนไม่บ่อย — คล้ายชนิดของตัวแปร
Instance
ข้อมูลจริง ณ เวลาใดเวลาหนึ่ง — คล้ายค่าปัจจุบันของตัวแปร
Physical data independence

ความสามารถในการเปลี่ยน physical schema โดยไม่ต้องเปลี่ยน logical schema หรือ application ที่พึ่งพา logical schema

จำ: Schema = แบบ / Instance = ภาพถ่าย ณ ตอนนั้น

DDL, DML และองค์ประกอบ DBMS

DDL — Definition

กำหนด schema, data types, constraints, indexes และ authorization เช่น CREATE TABLE, ALTER TABLE, DROP TABLE

DML — Manipulation

ค้นหรือเปลี่ยนข้อมูล เช่น SELECT, INSERT, UPDATE, DELETE

Storage manager

เชื่อมข้อมูลระดับต่ำกับ query/application และจัดการเก็บ-ค้น-แก้ข้อมูล

Query processor

Parsing/translation → optimization → evaluation

Transaction manager

รักษาความสอดคล้องเมื่อระบบล้มเหลวหรือมีงานพร้อมกัน

Relational Model และ Keys

พื้นฐานของตารางและ keys เชื่อมทั้งข้อทฤษฎี SQL constraints และการแปลง ER จึงควรเข้าใจเป็นระบบเดียวกัน

Relation schemaStudent(student_id, name, email, major)
Relation instanceชุด tuple ที่อยู่ใน Student ณ เวลาหนึ่ง
Tupleหนึ่งแถว เช่น (6600001, 'Somchai', 's@kku.ac.th', 'CoE')
Attributeหนึ่งคอลัมน์ เช่น major
Domainเซตค่าที่ attribute อนุญาต เช่น GPA เป็น DECIMAL 0.00–4.00
คุณสมบัติสำคัญ: relation เป็นเซตของ tuples ลำดับแถวไม่สำคัญ และค่า attribute โดยปกติต้องเป็น atomic (แบ่งต่อในโมเดลไม่ได้)

ลำดับความคิดของ Key

ระบุแถวไม่ซ้ำSUPERKEYตัดส่วนเกินCANDIDATE KEYเลือกใช้งานPRIMARY KEY
ชนิดนิยามตัวอย่างใน Student
Superkeyชุด attribute ที่ระบุ tuple ได้ไม่ซ้ำ อาจมี attribute เกินจำเป็น{student_id}, {email}, {student_id, name}
Candidate keyMinimal superkey: เอา attribute ตัวใดออกแล้วไม่ unique{student_id}, {email}
Primary keycandidate key ที่ผู้ออกแบบเลือกเป็นตัวระบุหลัก ควรคงที่{student_id}
Foreign keyattribute ใน referencing relation ที่อ้าง candidate/primary key ของ referenced relationEnrollment.student_id → Student.student_id
จุดหลอก: ถ้า {ID} เป็น candidate key แล้ว {ID, name} เป็น superkey แต่ ไม่ใช่ candidate key เพราะมี name เกินมา ส่วน email อาจ unique แต่เปลี่ยนได้ จึงมักไม่เหมาะเป็น primary key เท่า ID ที่ระบบสร้าง

Referential Integrity

ถ้า Enrollment มี student_id = 999 ค่านั้นต้องปรากฏเป็น key ใน Student ก่อน มิฉะนั้น FK constraint จะปฏิเสธการ insert โดยทั่วไป FK อาจเป็น NULL ได้ถ้าไม่ได้กำหนด NOT NULL

SQL พื้นฐาน: จากโจทย์สู่ Query

เริ่มทุกข้อด้วยการระบุ “ต้องแสดงคอลัมน์ใด”, “ข้อมูลอยู่ตารางใด”, “ต้องเชื่อมอย่างไร” และ “กรองแถวหรือกรองกลุ่ม” แล้วจึงเติม syntax

โครง Query และลำดับประมวลผล

SELECT [DISTINCT] column_or_expression AS alias
FROM table_name AS t
[JOIN other_table AS o ON t.key = o.key]
[WHERE row_condition]
[GROUP BY grouping_columns]
[HAVING group_condition]
[ORDER BY column_or_alias ASC|DESC];
FROM / JOINWHEREGROUP BYHAVINGSELECTDISTINCTORDER BY
เหตุผลที่ alias บางตัวใช้ใน WHERE ไม่ได้: DBMS ประเมิน WHERE ก่อน SELECT จึงยังไม่สร้าง alias จาก SELECT แต่ ORDER BY มาทีหลังและมักใช้ alias ได้

JOIN: เลือกชนิดจากแถวที่ต้องรักษา

อย่าจำจากภาพวงกลมอย่างเดียว ให้ถามว่า “ถ้าไม่มีคู่ตรงกัน โจทย์ยังต้องการแถวนั้นหรือไม่?” คำตอบจะบอกชนิด join

คำในโจทย์JOINผลลัพธ์
“ที่มี”, “ซึ่งทำงานอยู่”, “ที่ลงทะเบียนแล้ว”INNER JOINเฉพาะแถวที่มีคู่ทั้งสองฝั่ง
“ทุก A แม้ไม่มี B”, “including those with none”LEFT JOIN โดยวาง A ซ้ายA ครบ; คอลัมน์ B เป็น NULL เมื่อไม่มีคู่
“ทุก B แม้ไม่มี A”RIGHT JOIN หรือสลับตารางแล้ว LEFT JOINB ครบ
“ทุกแถวจากทั้งสองฝั่ง”FULL OUTER JOINmatched + unmatched ทั้ง A และ B

INNER JOIN สามตาราง

SELECT e.first_name, e.last_name,
       d.location, p.project_name
FROM employees AS e
JOIN departments AS d
  ON e.department = d.department_name
JOIN employee_projects AS ep
  ON e.employee_id = ep.employee_id
JOIN projects AS p
  ON ep.project_id = p.project_id;

ทุกพนักงาน แม้ยังไม่มีโครงการ

SELECT e.employee_id, e.first_name, p.project_name
FROM employees AS e
LEFT JOIN employee_projects AS ep
  ON e.employee_id = ep.employee_id
LEFT JOIN projects AS p
  ON ep.project_id = p.project_id;
Anti-join: หา A ที่ไม่มี B 
SELECT e.*
FROM employees e
LEFT JOIN employee_projects ep
  ON ep.employee_id = e.employee_id
WHERE ep.employee_id IS NULL;
Self join: เทียบพนักงานกับหัวหน้า 
SELECT e.name, e.salary,
       m.name AS manager, m.salary
FROM employees e
JOIN employees m
  ON e.manager_id = m.employee_id
WHERE e.salary > m.salary;

FULL OUTER JOIN ใน MySQL

SELECT a.id, a.name, b.detail
FROM A a LEFT JOIN B b ON a.id = b.a_id
UNION
SELECT a.id, a.name, b.detail
FROM A a RIGHT JOIN B b ON a.id = b.a_id;
NATURAL JOIN: เชื่อมทุกคอลัมน์ที่ชื่อเหมือนกันอัตโนมัติ สั้นแต่เสี่ยง หากสองตารางมีคอลัมน์ชื่อเดียวกันโดยบังเอิญผลอาจผิด ในข้อเขียนใช้ JOIN ... ON เพื่อแสดงเงื่อนไขชัดเจน เว้นแต่โจทย์ระบุ natural join

INTERSECTอยู่ทั้งสอง queryตาม set semantics
EXCEPTอยู่ query แรกแต่ไม่อยู่ query สองตาม set semantics
 
SELECT course_id FROM section
WHERE semester = 'Fall' AND year = 2026
UNION
SELECT course_id FROM section
WHERE semester = 'Spring' AND year = 2026;

ข้อบังคับ: แต่ละ SELECT ต้องคืนจำนวนคอลัมน์เท่ากัน และชนิดข้อมูลในตำแหน่งเดียวกันต้องเข้ากันได้

Aggregate, GROUP BY และ HAVING

หัวใจคือแยก “กรองแถวก่อนรวมกลุ่ม” ออกจาก “กรองผลสรุปหลังรวมกลุ่ม” และรู้ว่า NULL ถูกนับหรือข้ามอย่างไร

Aggregate functions

COUNT(*)
นับทุกแถว รวมแถวที่บางคอลัมน์เป็น NULL
COUNT(col)
นับเฉพาะแถวที่ col ไม่เป็น NULL
COUNT(DISTINCT col)
นับค่าที่ไม่ซ้ำและไม่เป็น NULL
SUM / AVG
รวม/เฉลี่ยค่าที่ไม่เป็น NULL
MIN / MAX
ค่าน้อย/มากสุด โดยข้าม NULL

Pattern ที่ออกสอบบ่อย

SELECT department,
       COUNT(*) AS employee_count,
       AVG(salary) AS average_salary
FROM employees
WHERE hire_date >= '2020-01-01'
GROUP BY department
HAVING COUNT(*) > 1
   AND AVG(salary) > 70000
ORDER BY average_salary DESC;
กฎ SELECT: ทุกคอลัมน์ใน SELECT ที่ไม่อยู่ใน aggregate function ต้องอยู่ใน GROUP BY เช่นเลือก department และ AVG(salary) ต้อง group by department
โจทย์ใช้เพราะ
เฉพาะพนักงาน IT ก่อนคำนวณWHERE department='IT'กรอง individual rows
เฉพาะแผนกที่มีพนักงานมากกว่า 5HAVING COUNT(*)>5COUNT เกิดหลัง grouping
แผนกที่เงินเดือนเฉลี่ยเกิน 70,000HAVING AVG(salary)>70000กรองค่าของกลุ่ม
Empty/all-NULL group: COUNT คืน 0 แต่ aggregate อื่นโดยทั่วไปคืน NULL เมื่อไม่มีค่าที่ไม่เป็น NULL

Subquery: WHERE, FROM, SELECT และ Correlation

เริ่มจากถามว่า inner query คืน “ชุดค่า”, “ตาราง”, หรือ “ค่าเดียว” แล้วเลือก IN/EXISTS/comparison ให้ตรงชนิดผลลัพธ์

IN, ANY/SOME, ALL และ EXISTS

-- อยู่ในชุดผลลัพธ์
SELECT * FROM employees
WHERE department_id IN (
  SELECT department_id
  FROM departments
  WHERE location IN ('New York','Chicago')
);
-- มีอย่างน้อยหนึ่งแถวที่สัมพันธ์กัน
SELECT d.* FROM departments d
WHERE EXISTS (
  SELECT 1 FROM employees e
  WHERE e.department_id = d.department_id
);
Predicateความหมายคำในโจทย์
x > ANY(subquery)มากกว่าอย่างน้อยหนึ่งค่าในชุดmore than at least one / some
x > ALL(subquery)มากกว่าทุกค่าในชุดmore than every / all
EXISTS(subquery)inner query คืนอย่างน้อยหนึ่งแถวthere exists / has at least one
NOT EXISTS(subquery)inner query ไม่คืนแถวnone / never / not assigned

Correlated subquery

Inner query อ้างแถวจาก outer query จึงประเมินโดยสัมพันธ์กับแต่ละแถว ตัวอย่าง “พนักงานที่ได้เงินมากกว่าค่าเฉลี่ยของแผนกตนเอง”:

SELECT e.employee_id, e.first_name,
       e.department, e.salary
FROM employees AS e
WHERE e.salary > (
  SELECT AVG(x.salary)
  FROM employees AS x
  WHERE x.department = e.department
);

Subquery ใน FROM และ SELECT

Derived table — คืน relation 
SELECT x.department, x.avg_salary
FROM (
  SELECT department, AVG(salary) avg_salary
  FROM employees
  GROUP BY department
) AS x
WHERE x.avg_salary > 70000;
Scalar subquery — ต้องคืนค่าเดียว 
SELECT d.department_name,
       (SELECT COUNT(*)
        FROM employees e
        WHERE e.department_id=d.id) AS n
FROM departments d;
กับดัก NOT IN + NULL: ถ้า subquery คืน NULL การเปรียบเทียบอาจกลายเป็น UNKNOWN และไม่คืนแถวตามคาด สำหรับ “ไม่มีความสัมพันธ์” มักใช้ NOT EXISTS ปลอดภัยกว่า

WITH / CTE

WITH above_average AS (
  SELECT *
  FROM employees
  WHERE salary > (SELECT AVG(salary) FROM employees)
)
SELECT a.first_name, d.department_name
FROM above_average a
JOIN departments d ON d.department_id = a.department_id;

CTE เป็นผลลัพธ์ตั้งชื่อชั่วคราวที่ใช้ได้ภายใน query เดียว ช่วยแบ่ง query ยาวให้คิดทีละส่วน

ข้อเติมโค้ดมักตรวจว่าเลือก data type เหมาะ วาง composite key ถูก และเขียน FK ให้จำนวน/ลำดับคอลัมน์ตรงกับ key ที่อ้าง

ตัวอย่างครบ: Parent, Child และ Junction Table

CREATE TABLE students (
  student_id VARCHAR(10) PRIMARY KEY,
  name       VARCHAR(80) NOT NULL,
  email      VARCHAR(120) UNIQUE,
  gpa        DECIMAL(3,2) CHECK (gpa BETWEEN 0 AND 4)
);

CREATE TABLE courses (
  course_id VARCHAR(10) PRIMARY KEY,
  title     VARCHAR(100) NOT NULL,
  credits   INT NOT NULL CHECK (credits > 0)
);

CREATE TABLE enrollments (
  student_id VARCHAR(10),
  course_id  VARCHAR(10),
  semester   VARCHAR(10),
  grade      VARCHAR(2),
  PRIMARY KEY (student_id, course_id, semester),
  FOREIGN KEY (student_id)
    REFERENCES students(student_id),
  FOREIGN KEY (course_id)
    REFERENCES courses(course_id)
);
Constraint แต่ละตัวป้องกันอะไร
  • PK: แถวซ้ำ/ไม่มีตัวระบุ
  • FK: orphan row และ reference ที่ไม่มีจริง
  • UNIQUE: ค่าธุรกิจซ้ำ เช่น email
  • NOT NULL: ข้อมูลบังคับหาย
  • CHECK: ค่านอก business rule
ลำดับสร้างตาราง

สร้าง referenced/parent table ก่อน referencing/child table ส่วนตอนลบมักต้องลบ child ก่อน parent มิฉะนั้น FK อาจขัดขวาง

DELETE ลบแถวแต่เก็บโครงสร้าง; DROP TABLE ลบทั้งข้อมูลและ table definition

เพิ่ม Constraint ภายหลัง

ALTER TABLE enrollments
ADD CONSTRAINT fk_enrollment_student
FOREIGN KEY (student_id)
REFERENCES students(student_id);

ER Modeling: หา Entity, Relationship และ Cardinality

อ่านสถานการณ์เหมือนแยกคำนามและคำกริยา แต่ต้องพิจารณาว่าแนวคิดนั้นควรเป็น entity, attribute หรือ relationship จากการใช้งานและกฎธุรกิจจริง

Entity
วัตถุโลกจริงที่แยกจากสิ่งอื่นได้ เช่น Student, Course
Entity set
กลุ่ม entities ชนิดเดียวกัน มี attributes เหมือนกัน
Attribute
คุณสมบัติที่อธิบาย entity/relationship เช่น name, since
Relationship
ความสัมพันธ์ระหว่าง entities ตั้งแต่สองชุดขึ้นไป เช่น Student enrolls Course
วิธีอ่าน Cardinality สองทิศ
  1. สำหรับ A หนึ่งตัว สัมพันธ์กับ B ได้สูงสุดกี่ตัว?
  2. สำหรับ B หนึ่งตัว สัมพันธ์กับ A ได้สูงสุดกี่ตัว?

“each / at most one” ชี้ไปฝั่ง 1
“many / several / multiple” ชี้ไปฝั่ง N

ตัวอย่างแปลข้อความ

Business ruleวิเคราะห์Cardinality
หนึ่ง department มีพนักงานหลายคน; พนักงานแต่ละคนอยู่ได้หนึ่ง departmentDept→Employee หลาย, Employee→Dept หนึ่งDepartment 1:N Employee

บุคคลมี passport ได้อย่างมากหนึ่งเล่ม และ passport เป็นของคนเดียวทั้งสองทิศอย่างมากหนึ่งPerson 1:1 Passport

Participation Constraints

Total participation

entity ทุกตัวต้องเข้าร่วม relationship อย่างน้อยหนึ่งครั้ง คำใบ้: every, must, required เช่น “พนักงานทุกคนต้องอยู่แผนก”

Partial participation

บาง entity อาจไม่เข้าร่วม คำใบ้: may, optional, not every เช่น “พนักงานอาจยังไม่ได้รับมอบหมายโครงการ”

Weak Entity

weak entity ไม่มี key ที่ระบุได้โดยลำพัง ต้องใช้ partial key + primary key ของ owner โดย owner กับ weak entity เป็น 1:N และ weak entity มี total participation ใน identifying relationship

Employee(emp_id PK, name)
Dependent(emp_id FK, dependent_name, relationship,
          PK(emp_id, dependent_name))

Entity หรือ Attribute?

  • ถ้ามีหลายค่าต่อ entity เช่น พนักงานมีหลาย address → มักแยก Address เป็น entity
  • ถ้าต้อง query โครงสร้างภายใน เช่น city/street → แยก composite attribute หรือ entity ให้ค้นได้
  • ถ้าข้อมูลขึ้นกับคู่ของ entities เช่น enrollment grade → เป็น relationship attribute

แปลง ER Diagram เป็น Relational Schema

ทำตามกฎคงที่: สร้างตาราง entity ก่อน จากนั้นวาง FK ตาม cardinality แล้วค่อยย้าย attributes ของ relationship และบังคับ participation

  1. Entity → Table: simple attribute เป็น column; composite attribute แตกเป็นส่วนย่อย; key เดิมเป็น PK
  2. หา cardinality: อ่านสองทิศและหา total/partial participation
  3. วาง FK: 1:N วาง key ฝั่ง 1 ในตารางฝั่ง N; M:N/ternary สร้างตารางใหม่
  4. ย้าย relationship attributes: ใส่ในตารางที่เป็นตัวแทน relationship
  5. ตรวจ constraints: PK, FK, UNIQUE สำหรับ 1:1 และ NOT NULL สำหรับ total participation

1:Nนำ PK ฝั่ง 1 ไปเป็น FK ฝั่ง NDepartment(dept_id PK)

กลยุทธ์ทำข้อสอบและรายการจุดพลาด

ข้อสอบสามชั่วโมงให้เขียนด้วยปากกา จึงควรวางโครงก่อนเขียนจริงและตรวจ syntax ที่มีผลต่อคะแนนมากกว่าความสวยของคำตอบ

ขั้นตอนแก้โจทย์ SQL

  1. วงคอลัมน์ที่โจทย์ต้องการแสดง → SELECT
  2. ระบุตารางต้นทางและเส้นทาง FK → FROM/JOIN
  3. แยกเงื่อนไขแถว → WHERE
  4. ถ้ามี “ต่อกลุ่ม/แต่ละ/จำนวน/เฉลี่ย” → GROUP BY
  5. เงื่อนไขบน COUNT/AVG/SUM → HAVING
  6. ตรวจ NULL, duplicate, unmatched rows และลำดับ

ข้อผิดพลาดที่ต้องจับ

  • ลืมเงื่อนไข JOIN → Cartesian product
  • ใช้ = NULL แทน IS NULL
  • ใช้ aggregate ใน WHERE แทน HAVING
  • SELECT คอลัมน์ที่ไม่ได้ aggregate/ไม่ได้ GROUP BY
  • ใช้ INNER ทั้งที่โจทย์ต้องการ “ทุกแถวแม้ไม่มีคู่”
  • NOT IN เจอ NULL แล้วผลหาย
  • วาง FK ผิดฝั่งใน 1:N หรือไม่สร้าง junction ใน M:N
  • เรียก superkey ที่มีส่วนเกินว่า candidate key

รูปแบบคำตอบ Short Answer

1. นิยามหนึ่งประโยค — “Candidate key คือ minimal superkey...”

2. เงื่อนไขหรือเหตุผล — “ถ้าเอา attribute ใดออกแล้วไม่ unique จึงถือว่า minimal”

3. ตัวอย่าง/ผลกระทบ — “{student_id} เป็น candidate แต่ {student_id,name} ไม่เป็น เพราะ name เกินมา”

สิ่งที่ไม่ควรใช้เวลาอ่านมากเกินไป

ตามประกาศขอบเขต หัวข้อ views, materialized views, indexes, authorization, database modification, ประวัติ DBMS และ NoSQL/NewSQL เป็นลำดับรอง อ่านเฉพาะเมื่ออาจารย์ย้ำเพิ่มเติม หลังจากทำ core SQL และ ER ได้แล้ว

โจทย์ทบทวนพร้อมเฉลย

ลองตอบบนกระดาษก่อนเปิดเฉลย โดยเฉพาะข้อ SQL ให้เขียน query เต็มพร้อม alias และ semicolon เพื่อจำรูปแบบการเขียนจริง

1) อธิบาย schema กับ instance และยกตัวอย่าง

Schema คือโครงสร้างเชิงตรรกะ เช่น Student(student_id, name, major) ส่วน instance คือชุดแถวจริงใน Student ณ เวลาใดเวลาหนึ่ง Schema คล้ายชนิดของตัวแปร ส่วน instance คล้ายค่าปัจจุบัน

2) ถ้า {student_id} unique แล้ว {student_id, email} เป็น key ชนิดใด?

เป็น superkey เพราะระบุ tuple ได้ไม่ซ้ำ แต่ไม่ใช่ candidate key เพราะ email เป็นส่วนเกิน; เอา email ออกแล้ว {student_id} ยัง unique

3) เขียน relational algebra: ชื่อนักศึกษา CoE ที่ GPA มากกว่า 3.5
π name (σ major='CoE' ∧ gpa>3.5 (Student))
4) หา employee ที่เงินเดือนมากกว่า 70,000 และอยู่ IT หรือ Finance
SELECT *
FROM employees
WHERE salary > 70000
  AND department IN ('IT', 'Finance');
5) แสดงทุก department พร้อมจำนวน employee รวม department ที่ไม่มี employee
SELECT d.department_id, d.department_name,
       COUNT(e.employee_id) AS employee_count
FROM departments d
LEFT JOIN employees e
  ON e.department_id = d.department_id
GROUP BY d.department_id, d.department_name;

ใช้ LEFT JOIN เพื่อเก็บ department ครบ และ COUNT(e.employee_id) เพื่อให้แผนกไม่มีพนักงานนับเป็น 0; ถ้าใช้ COUNT(*) จะนับแถว outer join เป็น 1

6) หา department ที่มีพนักงานมากกว่า 2 คนและเงินเดือนเฉลี่ยเกิน 70,000
SELECT department,
       COUNT(*) AS n,
       AVG(salary) AS avg_salary
FROM employees
GROUP BY department
HAVING COUNT(*) > 2
   AND AVG(salary) > 70000;
7) WHERE กับ HAVING ต่างกันอย่างไร?

WHERE กรอง individual rows ก่อน grouping และไม่ใช้ aggregate condition; HAVING กรอง groups หลัง GROUP BY จึงใช้ COUNT/AVG/SUM ได้

8) หา employee ที่ได้เงินมากกว่าค่าเฉลี่ยของแผนกตนเอง
SELECT e.*
FROM employees e
WHERE e.salary > (
  SELECT AVG(x.salary)
  FROM employees x
  WHERE x.department = e.department
);
9) หา employee ที่ยังไม่ถูกมอบหมายโครงการ โดยหลีกเลี่ยงปัญหา NULL
SELECT e.*
FROM employees e
WHERE NOT EXISTS (
  SELECT 1
  FROM employee_projects ep
  WHERE ep.employee_id = e.employee_id
);
10) COUNT(*), COUNT(manager_id) และ COUNT(DISTINCT department) ต่างกันอย่างไร?

COUNT(*) นับทุกแถว; COUNT(manager_id) นับเฉพาะแถวที่ manager_id ไม่เป็น NULL; COUNT(DISTINCT department) นับค่า department ที่ไม่ซ้ำและไม่เป็น NULL

11) แปลง Student M:N Course ที่ relationship มี semester และ grade
Student(student_id PK, ...)
Course(course_id PK, ...)
Enrollment(student_id FK,
           course_id FK,
           semester,
           grade,
           PK(student_id, course_id, semester))

ต้องรวม semester ใน PK เพราะนักศึกษาคนเดิมอาจเรียนวิชาเดิมต่างภาคการศึกษา

12) Department 1:N Employee และ employee ทุกคนต้องมี department จะแปลงอย่างไร?
Department(dept_id PK, dept_name)
Employee(emp_id PK, name,
         dept_id FK NOT NULL
         REFERENCES Department(dept_id))

FK อยู่ฝั่ง N และ NOT NULL บังคับ total participation ของ Employee

13) Weak entity Dependent มี partial key = name และ owner = Employee
Employee(emp_id PK, ...)
Dependent(emp_id FK,
          name,
          relationship,
          PK(emp_id, name))
14) ทำไม FULL OUTER JOIN ใช้ตรง ๆ ไม่ได้ในตัวอย่าง MySQL และจำลองอย่างไร?

MySQL ตามเอกสารรายวิชาไม่รองรับ FULL OUTER JOIN โดยตรง จึงรวม LEFT JOIN กับ RIGHT JOIN ด้วย UNION

SELECT ... FROM A LEFT JOIN B ON ...
UNION
SELECT ... FROM A RIGHT JOIN B ON ...;
15) ตรวจ query นี้: SELECT department, name, AVG(salary) FROM employees GROUP BY department;

name ไม่ได้อยู่ใน aggregate function และไม่ได้อยู่ใน GROUP BY จึงไม่ชัดว่าจะเลือกชื่อใดจากแต่ละกลุ่ม ควรลบ name หรือเพิ่ม grouping ตามความหมายที่โจทย์ต้องการ
